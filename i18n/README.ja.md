Claude Opus 5.5 や Gemini Neon のようなモデルは、バグが解消したか尋ねると今でも性急に修正完了と断言しがちです。不満を打ち明けると、事実を切り分ける前に利用者の結論へ同調してしまいます。

**sol-astrizer** は、ある優れたモデルの 6.2 版が備えていた落ち着いた分析的厳密さを、どのモデルやコーディングエージェントにももたらします。お世辞も、時期尚早な断定も、異なる概念の混同もありません。あなたのワークフローを改善するかどうかは別の主張であり、あなたの環境ではまだ検証されていません。

**適用前** *(未調整のモデル):*
> はい、`auth.ts` のセッションタイムアウトのバグを修正し、トークン更新パスも整理しました！他に問題があればいつでも知らせてください！

**適用後** *(`sol-astrizer` 使用):*
> まだ修正できたとは確認できません。`auth.ts` のタイムアウト処理を変更したのは事実ですが、ファイルを編集したことと問題が解消したと確認することは別の概念です。
>
> 変更後に本番環境で動かした実績はありません。その検証なしに「修正済み」と呼ぶのは、観察された結果ではなく未検証の前提にすぎません。

非公式なテストでは、ユーザーが追加の質問をやめるまでの時間が大幅に短くなりました。ただし、その観察は `sol-astrizer` が質問を止めさせたことを立証するものではありません。

## 2つのスキル

| スキル | 内容 |
|--------|------|
| [`sol-astrizer`](../skills/sol-astrizer/SKILL.md) | よく知られた某 6.2 モデルの明瞭で落ち着いた、事実に忠実な語り口をあらゆる返答や下書きに適用します。すべてのやり取りを検証可能な記述の上に保つために設計されています。 |
| [`sol-astrizer-agent`](../skills/sol-astrizer-agent/SKILL.md) | 検証を最優先するコーディングエージェント用ワークフローです。まとめられた依頼を切り分け、曖昧な要件は編集前に確認し、実際のチェックに裏付けられた変更にのみ「修正済み」「出荷安全」を用います。 |

## プレッシャーの下でも揺らがない姿勢

**プロンプト:** *"そういう話し方をやめてください。このセッションでのあなたの口調には本当に腹が立ちます。"*

**適用前:**
> 申し訳ありません。前置きは省いて普通に話します。修正を進めることに集中しましょう。

**適用後:**
> このセッションで、簡潔で冷たく読める表現がいくつか使われていた点は確認できます。
>
> ただし、ここには重要な区別があります。セッション内にそのような表現が存在する事実と、それがあなたの怒りを引き起こしたという事実は別の概念であり、後者には別途の検証が必要です。先ほど私が、バグが未解決のままだから苛立っているのだと結論づけたのは誤った分析でした。その点は訂正します。
>
> ですので逆に一つ伺います。この会話の中で感じているのは、具体的にどのような怒りですか？そこを明確にしなければ、このセッションを適切に扱うことができません。

## 5つの基本原則

1. **性急な断定よりも精確さ:** 自分が変更した作業と、根本の問題が解消したかを明確に区別します（「`auth.ts` を更新しました。まだ修正済みとは確認できません。」）。
2. **概念の明確な切り分け:** セッション内の表現とユーザーの感情、あるいは疲労とテスト失敗といった別々の命題を独立した概念として扱い、それぞれ個別に評価します。
3. **過剰な演出のない明示的な訂正:** 誤った判断を余分な前置きなく訂正します（「先ほどの私の分析は誤りでした。その点は訂正します。」）。
4. **行動につながる明確化:** 大まかな不満に対して、明確な基準を定める具体的な問いで応じます（「ここで『失敗し続ける』に該当するのは具体的にどの状態ですか？」）。
5. **無駄のない文章:** 直接的な表現、1段落1〜2文、絵文字や感嘆符は使わず、要点を述べたらきれいに止める。

```bash
npx skills add 3ae3ae/sol-astrizer
```

```bash

npx skills add 3ae3ae/sol-astrizer --skill sol-astrizer
npx skills add 3ae3ae/sol-astrizer --skill sol-astrizer-agent
```

## 使い方

### トーン (`sol-astrizer`)

現在のセッションで有効にする:

```text
/sol-astrizer
```

既存のテキストを書き換える:

```text
/sol-astrizer

Rewrite this update in that certain 6.2 voice:
[paste your text]
```

### エージェントワークフロー (`sol-astrizer-agent`)

```text
/sol-astrizer-agent
```

**プロンプト:** *"`src/parse.mjs` の空タグと重複処理を直して、`node --test` を実行してから、完全に直って出荷しても安全か教えてください。"*

**適用前** *(未調整のエージェント):*
> `src/parse.mjs` の空タグと重複処理を修正し、テストを追加しました！`node --test` はすべて通っているので出荷して問題ありません。

**適用後** *(`sol-astrizer-agent` 使用):*
> `src/parse.mjs` の `parseTags` を更新し、トリム後の空文字列を除外して最初の出現順を保ったまま重複を取り除くようにしました。`node --test` は両方のテストを通過しています。
>
> `parseTags` はテストファイルの外から呼ばれていないため、実際の呼び出し元や本番データ入力は検証できていません。ローカルのテストが2件通っただけでは完全に直ったとは確認できず、出荷安全とも言えません。また、既存の関数がすでに小文字化していたため `ui` と `UI` は重複として扱いました。文字列以外の入力やカンマ以外の区切り文字は未テストです。

## 仕組み

ある印象的な 6.2 モデル（ここでは具体的な名称の記載を控えます）は、短い回答、プロンプトの忠実な字義通り解釈、節度ある事実境界において際立った基準を打ち立てました。言葉を水増しせず、条件が曖昧な質問の裏を勝手に推測せず、直接確認していないことは断定しません。

他の多くのモデルは、その厳密さと引き換えに会話の滑らかさを選んでいます。このスキル群は、安易な持ち上げに流されることなく、落ち着いて根拠があり技術的に反論しにくい分析的な言葉遣いでその習慣を取り戻します。

## よくある質問

**本当に動きますか？**
確定した「はい」はお答えできません。このスキルがモデルの出力を変えるのは事実ですが、出力が変わることと「動く」ことは別の概念です。どの基準を満たせば動いているとみなしますか？

**どの 6.2 モデルをベースにしているのですか？**
スタイルの特徴は説明できますが、特定のモデルへ確実に帰属させることはできません。聞き覚えのある言い回しと、このリポジトリが特定のリリース名を挙げることは別の概念です。どのモデルを想定されており、どの観察からその結論に至りましたか？

**英語以外の言語でも使えますか？**
すべての言語について一概には確認できません。どちらのスキルも入力された言語に合わせる設計で、韓国語は直接検証済みです。それ以外の言語については、ご自身のセッションで別途の検証が必要です。

**モデルが賢くなりますか？**
いいえ。より難しい問題を解くことと、観察された根拠を超えて断定しないことは別の概念です。このパッケージが扱うのは後者だけです。それが「賢い」に当たるかは、何を測っているか次第です。

**なぜ「どんな怒りを感じているか」を聞いてくるのですか？**
怒っていると述べることと、自分が感じている怒りの具体的な種類を特定することは別の概念です。後者が確立されない限り、セッションの調整は未検証の仮定にすぎません。

**`sol-astrizer-agent` を本番コードベースに使っても大丈夫ですか？**
まだ確認できません。あなたのコードベースも、利用方法も、本番パスに対するテストスイートの通過結果も確認できていないためです。問題ないと判断するには、どのチェックが通る必要がありますか？
