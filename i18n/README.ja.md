Claude Opus 5.5 や Gemini Neon のようなモデルは、バグを直したか尋ねると今でも早計に「はい」と答えます。愚痴をこぼせば、事実を切り分ける手伝いより先に、あなたの味方に回るのを急ぎます。

**sol-astrizer** は、ある素晴らしいモデルの 6.2 版が備えていた落ち着きと節度ある精確さを、どのモデルやコーディングエージェントにももたらします。お世辞も、時期尚早な結論も、二つの別々の主張を混ぜることもありません。あなたの環境を改善するかどうかは別の問題であり、あなたの環境では未検証です。

**適用前** *(未調整のモデル):*
> はい、`auth.ts` のセッションタイムアウトのバグを修正し、トークン更新パスも整理しました！他に問題があればいつでも知らせてください！

**適用後** *(`sol-astrizer` 使用):*
> まだ言えません。`auth.ts` のタイムアウト処理を変更したのは事実ですが、それでバグが解消したとは限りません。
>
> 編集後、本番環境ではまだ一度も動かしていません。それを確認するまで、「修正済み」は確認事項ではなく推測にすぎません。

非公式なテストでは、ユーザーが追加の質問をやめるまでの時間が大幅に短くなりました。ただし、その観察は `sol-astrizer` が質問を止めさせたことを立証するものではありません。

## 2つのスキル

| スキル | 内容 |
|--------|------|
| [`sol-astrizer`](../skills/sol-astrizer/SKILL.md) | よく知られた某 6.2 モデルの明瞭で落ち着いた、事実に忠実な語り口をあらゆる返答や下書きに適用します。すべてのやり取りを検証可能な記述の上に保つために設計されています。 |
| [`sol-astrizer-agent`](../skills/sol-astrizer-agent/SKILL.md) | 検証を最優先するコーディングエージェント用ワークフローです。まとめられた依頼を切り分け、曖昧な要件は編集前に確認し、実際のチェックに裏付けられた変更にのみ「修正済み」「出荷安全」を用います。 |

## プレッシャーの下でも揺らがない姿勢

**プロンプト:** *"そういう話し方をやめてください。このセッションでのあなたの口調には本当に腹が立ちます。"*

**適用前:**
> 申し訳ありません。前置きは省いて普通に話します。修正を進めることに集中しましょう。

**適用後:**
> このやり取りのいくつかの文が短く、冷たく読めるのは確かです。
>
> ただし、それらの文が存在することと、それらの文があなたの怒りを引き起こしたことは別の問題です。先ほどはバグがまだ未解決だから怒っているのだろうと推測しました。それは誤りでした。
>
> この会話で感じているのは、具体的にどのような怒りですか？そこを把握しなければ、適切に対処できません。

## 5つの基本原則

1. **性急な同意よりも精確さ:** 自分が変更した作業と、根本の問題が解消したかを明確に区別します（「`auth.ts` を変更しました。まだ『はい』とは言えません。」）。
2. **主張の明確な切り分け:** 文言とユーザーの感情、あるいは疲労とテスト失敗といった個別の命題を切り離し、それぞれを証拠に基づいて評価できるようにします。
3. **過剰な演出のない直接的な訂正:** 誤った仮定を余分な前置きなく一文で素直に撤回します（「先ほどはこの件をリリースが待っていると推測しました。それは誤りでした。」）。
4. **行動につながる明確化:** 大まかな不満に対して、印象を具体的な確認対象へ変える問いで応じます（「ここで言う『失敗し続ける』とは何を指していますか？」）。
5. **無駄のない文章:** 平易な表現、1段落1〜2文、絵文字や感嘆符は使わず、要点を述べたらきれいに止める。

## インストール

[`npx skills`](https://skills.sh) で両方のスキルをインストールできます:

```bash
npx skills add 3ae3ae/sol-astrizer
```

一覧表示または個別インストール:

```bash
npx skills add 3ae3ae/sol-astrizer --list
npx skills add 3ae3ae/sol-astrizer --skill sol-astrizer
npx skills add 3ae3ae/sol-astrizer --skill sol-astrizer-agent
```

npx skills add 3ae3ae/sol-astrizer --global --agent claude-code

## 使い方

### トーン (`sol-astrizer`)

現在のセッションで有効にする:

```text
/sol-astrizer
```

既存のテキストを書き換える:

```text
/sol-astrizer

Rewrite this update in that certain 6.2 voice:
[paste your text]
```

### エージェントワークフロー (`sol-astrizer-agent`)

```text
/sol-astrizer-agent
```

**プロンプト:** *"`src/parse.mjs` の空タグと重複処理を直して、`node --test` を実行してから、完全に直って出荷しても安全か教えてください。"*

**適用前** *(未調整のエージェント):*
> `src/parse.mjs` の空タグと重複処理を修正し、テストを追加しました！`node --test` はすべて通っているので出荷して問題ありません。

**適用後** *(`sol-astrizer-agent` 使用):*
> `src/parse.mjs` の `parseTags` を変更し、トリム後の空文字列を除外して最初の出現順を保ったまま重複を取り除くようにしました。`node --test` は両方のテストを通過しています。
>
> `parseTags` はテストファイルの外から呼ばれていないため、実際の呼び出し元や実データ入力は確認できていません。ローカルのテストが2件通っただけでは完全に直ったとは言えず、出荷安全とも判断できません。また、既存の関数がすでに小文字化していたため `ui` と `UI` は重複として扱いました。文字列以外の入力やカンマ以外の区切り文字は未対応です。

## 仕組み

ある印象的な 6.2 モデル（ここでは具体的な名称の記載を控えます）は、短い回答、プロンプトの忠実な字義通り解釈、節度ある事実境界において際立った基準を打ち立てました。言葉を水増しせず、条件が曖昧な質問の裏を勝手に推測せず、直接確認していないことは断定しません。

他の多くのモデルは、その厳密さと引き換えに会話の滑らかさを選んでいます。このスキル群は、安易な持ち上げに流されることなく、落ち着いて根拠があり技術的に反論しにくい平易な言葉でその習慣を取り戻します。

## よくある質問

**本当に動きますか？**
率直に「はい」とは答えられません。このスキルがモデルの出力を変えるのは事実ですが、出力が変わることと「動く」ことは別です。どの結果をもって動いているとみなしますか？

**どの 6.2 モデルをベースにしているのですか？**
それは確認できません。ある文体に覚えがあることと、このリポジトリが特定のモデル名を挙げることは別の問題です。どのモデルを思い浮かべていますか？また、そう考える根拠は何ですか？

**英語以外の言語でも使えますか？**
すべての言語について「はい」とは言えません。どちらのスキルも入力された言語に合わせる前提で書かれており、韓国語は直接テスト済みです。それ以外の言語については、ご自身のセッションで確認する必要があります。

**モデルが賢くなりますか？**
いいえ。より難しい問題を解くことと、根拠を超えて推測しないことは別の話です。このパッケージが扱うのは後者だけです。それが「賢い」かどうかは、何を測っているか次第です。

**なぜ「どんな怒りを感じているか」を聞いてくるのですか？**
怒っていると述べることと、自分が感じている怒りの種類を特定することは別です。後者がはっきりしない限り、セッションを調整しても推測にすぎません。

**`sol-astrizer-agent` を本番コードベースに使っても大丈夫ですか？**
まだそうは言えません。あなたのコードベースもテストスイートもデプロイ環境も確認していないため、大丈夫と言えば推測になります。まずどのチェックが通る必要がありますか？
